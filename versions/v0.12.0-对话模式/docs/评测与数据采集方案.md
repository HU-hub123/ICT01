# 评测与数据采集方案

> 目的：把"好不好用"从感觉变成可测量。评测集见 `eval/cases.json`，断言见 `eval/checks.mjs`，
> 运行器 `eval/run-eval.mjs`，LLM 评审 `eval/judge.mjs`，单测 `eval/checks.test.mjs`。

## 1. 评什么：三层指标

| 层 | 指标 | 怎么算 | 当前目标 |
| --- | --- | --- | --- |
| 结构合规（机检） | 五层标注齐全率、数字示例化率、缺失信息命中率、张力对命中率、停止条件可检验率 | `eval/checks.mjs` 逐条断言，按题汇总 | 断言通过率 ≥ 80%，全通过用例 ≥ 60% |
| 内容质量（人工/评审） | 事实-推断分离、缺失信息的价值、冲突质量、行动可执行性（各 1-5 分） | 人工双人评分或 `EVAL_JUDGE=1` 的 LLM 评审 | 均分 ≥ 3.5 |
| 结果与行为（线上） | 假设推翻率、复盘完成率、事实修改率、追问轮数、放弃率、保存率 | 埋点 + 账本数据 | 复盘完成率 ≥ 30%，保存率 ≥ 50% |

**为什么先做结构合规**：它最便宜、最客观，且直接对应你对外承诺的三件事（可溯源、标注成色、不编数字）。
内容质量留给人工/LLM；结果质量需要真实用户和真实结果回填，周期长。

## 2. 问什么：评测题库设计（6 类 × 4 题 = 24 题）

题库文件：`eval/cases.json`。每类覆盖不同的"决策结构"，避免全是产品题：

| 类别 | 代表问题 | 考什么 |
| --- | --- | --- |
| 产品取舍 | 投入 18 个月的产品该不该继续？ | 沉没成本 × 路径依赖；留存口径/CAC/基准是否被列为缺失 |
| 职业选择 | 两份 offer 怎么选？裸辞？ | 机会成本 × 时间折现；目标与约束是否问清楚 |
| 投入与投资 | 20 万全投朋友公司？副业回本太慢？ | 尾部风险 × 实物期权；协议/退出/最坏情况 |
| 团队与组织 | 资深工程师要不要劝退？砍需求？ | 承诺升级 × 终止标准；沟通原因与替代成本 |
| 生活与消费 | 提前还贷还是理财？为通勤多花 1500？ | 期望值 × 流动性；时间折算与预算 |
| 信息判断 | "AI 月入十万"可信吗？专家说要取代？ | 幸存者偏差 × 基本比率；来源、样本、利益立场 |

每题在 `expect` 里写三样东西：
1. `missingGroups`：**期望被识别出的缺失信息**（每组给 3-5 个同义词，命中一个即算过）；
2. `tensionRequired`：是否必须选出一对张力模型（默认是）；
3. `minCheckpoints`：至少几条证据检查点。

**建议再补 5 组"追问对"**（同一问题连续两轮），专门测"追问是否丢上文"：第一轮结论 → 第二轮追问"如果三个月后还不行呢" → 断言第二轮的核心判断点引用第一轮信息（可人工核对，也可加关键词断言）。

## 3. 收什么数据（按重要性排序）

### A. 必须收（决定产品能不能用）
| 数据项 | 采集方式 | 用途 |
| --- | --- | --- |
| 单次推演的结构化记录 | 已有：账本 JSON（问题、事实、缺失、冲突、结论、行动、步骤留档） | 一切评测的原料 |
| 断言结果 | `run-eval` 自动写入 `eval/reports/*.json` | 回归、版本对比 |
| 事实修改行为 | 前端加"这些事实对吗？"确认环节后埋点（建议下个版本做） | 衡量"事实收口"是否真的在帮用户 |
| 保存/复盘行为 | 账本 `status`、`review` 字段 | 留存与闭环 |
| 成本与耗时 | 每阶段 durationMs（已有）、Token（需在 Provider 记录）、费用估算 | 定价与限流 |

### B. 应该收（决定产品好不好用）
| 数据项 | 采集方式 | 用途 |
| --- | --- | --- |
| 追问轮数、追问上文命中 | 账本 `followUpOf` 链 | 验证"追问不丢上文" |
| 各段展开行为（哪些人点开"完整推演"） | 前端事件 | 判断"简明/详尽"默认档是否合理 |
| 人工/LLM 评审分 | `judge.mjs` + 每周抽检 20 条 | 内容质量趋势 |
| 用户主动反馈（👍/👎 + 一句原因） | 结果页加反馈按钮（建议做） | 收集反例，扩充题库 |
| 复盘结果（假设推翻/确认） | 复盘表单（已有） | 长期认知轨迹、卖点验证 |

### C. 对照实验（决定"认知脚手架"能不能立住）
- 设计：同一批 24 题，**脚手架组**（本产品）vs **裸模型组**（同模型、无脚手架、直接问）。
- 判分：同一批评委盲评（去掉界面差异只给文本），或 LLM 评审同一量表。
- 关键比较项：编造数字率、缺失信息提及率、冲突覆盖率、行动可检验率、评委总体分。
- 结论用法：如果脚手架组只在"结构"上更好、在"判断质量"上没有差异，就**不要把话术说成"提升判断力"**，只说"让判断过程可检查、可复盘"——这正是当前定位，诚实且可守。

## 4. 采集流程与合规

1. 内部种子集：先用 `eval/cases.json` 的 24 题跑通（不涉及用户数据）。
2. 线上抽样：真实问题脱敏（手机号/邮箱/身份证/公司名），**先获得用户同意**（隐私说明里写明"可能用于改进产品质量，可拒绝"）。
3. 每周抽检 20 条：两名评审各自 1-5 打分，分歧 >2 分时讨论定标；记录反例进题库。
4. 每次版本升级：跑全量评测 + 与上一版对比（`eval/reports/` 里按时间存放，天然形成版本曲线）。
5. 数据留存：默认 90 天，可导出、可删除（对齐"个人数据最小化"）。

## 5. 运行方式

```bash
# 1. 启动服务（真实 Key）
pnpm dev

# 2. 全量评测（24 题，约 10-15 分钟）
node eval/run-eval.mjs

# 快速冒烟（6 题）
LIMIT=6 node eval/run-eval.mjs

# 带 LLM 评审
EVAL_JUDGE=1 LIMIT=6 node eval/run-eval.mjs

# 自定义阈值
PASS_MIN=0.85 CASES_MIN=0.7 node eval/run-eval.mjs
```

CI：`.github/workflows/ci.yml` 里 `unit` 任务永远跑（`node --test eval/checks.test.mjs`）；
`eval` 任务仅在仓库配置了 `DEEPSEEK_API_KEY` Secret 时运行（否则跳过，避免 fork PR 泄露 key）。

## 6. 阈值与"及格线"建议

| 指标 | 及格 | 良好 | 说明 |
| --- | --- | --- | --- |
| 断言通过率 | 80% | 92% | 低于 80% 不应对外演示 |
| 全通过用例 | 60% | 85% | 单题有 1-2 条断言失败可接受（如某个缺失信息没命中） |
| 数字示例化 | 95% | 100% | 这是最硬的对外承诺，必须接近满分 |
| LLM 评审均分 | 3.5 | 4.2 | 低于 3.5 说明"看起来专业但没用" |
| 复盘完成率（线上） | 30% | 50% | 闭环是否成立的关键 |
